# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

Scribe is a Svelte 5 document editor/viewer published as the web component `<scribe-interpreter>` (also `<scribe-bindings-panel>`, `<scribe-component-renderer>`, `<scribe-component-slot>` and `<scribe-empty-content>`) plus `scribe.css`. The package is `@antonii22/scribe2` on GitHub Packages. Runes mode is forced by `svelte.config.js`.

## Commands

- `npm run dev`: SvelteKit playground with examples at `/examples/*` (`full`, `full-edit`, `edit-empty`, `full-edit-custom-binding`, `full-webcomponent`, `full-webcomponent-edit`).
- `npm run check` (svelte-check), `npx eslint src/lib src/routes`, `npm run build:wc` (web component bundle, types, `scribe.css` and the source of `src/lib/svelte/` into `dist/`).
- `npm test` runs the unit tests once (`vitest run`, node environment, config in `vitest.config.ts`). One file: `npx vitest run src/lib/utils/textFormat.test.ts`; one test by name: `npx vitest run -t "escape"`. `npm run test:watch` is for the maintainer, as it never exits.
- Tests are `*.test.ts` files next to the code they cover (`src/**`), and `tsconfig.types.json` excludes them from the published types. They cover pure code only (`utils/`, and stores that need no DOM): there is no DOM environment, so Svelte components and DOM code such as `parseDOM` are verified by hand in the examples. A test that fails is a bug to report, not a test to weaken. Run `npm test` after any change to `utils/textFormat*.ts`, and add a test for any new pure logic.
- `/examples/full-webcomponent-edit` loads `dist/` (gitignored), so run `npm run build:wc` before checking it.
- After renaming or removing a method of a store class, restart `npm run dev`. Stale HMR modules once produced `this.<oldName> is not a function` although the source was correct.

## Architecture

- `src/lib/index.ts` is the public API (`Scribe`, `getDefaultRegistry`, `defaultRegistry`, types, i18n, focus helpers). Changing anything exported there changes a published API. **`sideEffects` in `package.json`:** `dist/scribe.js` registers the custom elements when it is imported, so it is listed (`["**/*.css", "./dist/scribe.js"]`); without it a production build drops a bare `import '@antonii22/scribe2'` and no element is defined. Reproduced in a Vite project that only does that import, from an `npm pack` tarball: Vite 8 (Rolldown) and Vite 7 (Rollup 4.68) both emitted about 1 kB of JS and no tag registered with the old value, and about 2.5 MB with all five tags registered and the document drawn with the new one. Keep the file out of the list only if it ever loses its import effects, and list any new entry with module-level effects. `dist/svelte/mount.svelte.js` only exports functions, so it stays out on purpose. The second public entry is `@antonii22/scribe2/svelte` (`src/lib/svelte/mount.svelte.js` + its hand-written `.d.ts`): `createSvelte5Mount` and `createSvelteItemRenderer`, with an optional `context` passed to `mount()` (a component mounted by Scribe is a new root, so the host's Svelte context is not inherited). It is **published as source, not bundled**: `dist/scribe.js` carries its own Svelte runtime, so a helper exported from it would mount the components of the host with another runtime. `build:wc` copies the folder to `dist/svelte/` (`tsc` does not emit hand-written `.d.ts`), and `exports["./svelte"]` has the conditions `types`, `svelte` and `default`, so the host's bundler compiles it with its own Svelte. The file may import only `svelte` (`mount.test.ts` checks it), never anything of Scribe. The bundle uses the same file for the default components, which is right as they are compiled with its runtime. The README documents it for hosts.
- `components/Scribe.svelte` is the root and declares the custom element with `shadow: 'none'`, so styles are global. A new prop needs three edits: `types/ScribeProps.ts`, the `customElement.props` list and the `$props()` destructure. See `showBindingsPanel` and `showPrintButton`.
- `stores/*.svelte.ts` are singletons built on `$state` classes, so only one Scribe per page is supported (`Scribe.svelte` warns when a second one mounts):
  - `edit-store`: every document mutation. `insertComponent` modes are `after`, `before`, `replace` and `split`. **Components live in a container: the content of a section or a slot (see "Slots")**, so insert, delete, duplicate and merge resolve the container of the target first (`locate`, `readEntries`, `writeEntries`) and never touch `section.content` directly. `insertComponent` takes `options.slot` for where to append when there is no target. Usages of default bindings are not tracked in `customBindingUsages` (a public type): `getBindingUsages(id)` walks the document when asked, and the delete confirmation of a variable uses it.
  - `selection-store`: selected component or insertion point, plus the caret source.
  - `toolbar-store`: the add-component dropdown.
  - `value-dialog-store`: opens the dialog that sets the value of a component. `Scribe.svelte` renders `ComponentValueDialog` once, and both the ribbon's Set value and the action buttons of the empty states open it with this store.
  - `text-format-store` (UI state: follows the caret or marked fragment of the focused text, its formats and the pending format; used by the bold, italic, underline and strikethrough options of the `text` component), `global-registry`, `binding-store`, `custom-bindings-store`.
- `registry/`:
  - `defaultRegistry.ts`: `getDefaultRegistry(i18n)`, where `i18n` is required.
  - `ComponentRegistry.ts`: the component contract. A block component can define `height: { default, min, max }` (px), so it is drawn as a box of that height, and `isResizeable: true` (which requires the height) lets the user change it while it is selected. The chosen height is stored in `BlockComponent.height`.
  - `ComponentEditOptions.ts`: the buttons of the top toolbar (the ribbon). Options are drawn in groups by their `group` title, as large buttons when they have a `label` or small icons otherwise. `isSelected` and `isDisabled` receive `{ sectionId, componentId, value, config }` and are evaluated reactively in the `ComponentEditor` template, so they can read stores without the buttons being mounted again. An option can draw itself with `render`. In the click data, `insertion` is a getter: capturing the caret can save a new text (a ghost), so only the options that need it (Add) should read it. An option can declare a `shortcut` (`Mod+D`, `Mod+Shift+X`, `Ctrl+Space`, `Delete`; `Mod` is Ctrl, or Command on a Mac). Parsing, matching and the conflict check are pure code in `utils/shortcuts.ts` (tested). `ComponentEditor` listens to `keydown` on the document and runs a shortcut by clicking the option's button (found by `data-option-type`), so it behaves as the mouse does. It ignores keys that something already handled (`defaultPrevented`: the text keeps its own Ctrl+Space, which opens the add dropdown at the caret), dialogs and menus, and shortcuts without Ctrl, Mod or Alt while typing in a field (so `Delete` still deletes characters). `ComponentEditorButton` shows the shortcut in a bits-ui Tooltip (one `Tooltip.Provider` per button, as options that mount themselves have no context). Default shortcuts follow one scheme, so new options should too: component actions Ctrl+Space, `Mod+D`, `Delete`; Set value `Mod+K` (link to a value) and the chart data config `Mod+Shift+K`; text formats `Mod+B/I/U` and `Mod+Shift+X`; image alignment `Mod+Shift+L/E/R` (as in Google Docs); and `Alt+Shift+N` for the Nth option of a group (image fit, chart type, map controls, table options, QR dots, text-input layout). Avoid `Mod+Alt+…` (AltGr on Windows types `@` and `|`), `Mod+Shift+digit` (screenshots on a Mac) and plain letters, and note that shortcuts without Ctrl, Mod or Alt never run while typing (so the text input, which is selected by focusing it, still gets its `Alt+Shift+N`). On a Mac an Alt shortcut wins over the Option character it would type, so custom options should use digits, whose symbols are rarely typed, and not letters. `globalRegistry.initialize` warns in the console when options of one component share a shortcut or one is invalid; components are not compared with each other, as only the selected one is active.
- `components/component/`: `ComponentRenderer` (the `.component-edit-contents` wrapper, hover highlight, selection ring and label, the box with the height of a sized block and its resize handle; a block component must fill that box with `flex: 1` or `height: 100%` and `min-height: 0` instead of fixing its own height, as what does not fit is cut off), `ComponentEditor` (the options of the selected component as titled groups of buttons, used only by the top toolbar) and `ComponentToolbar` (the add-component dropdown).
- `EmptyContent` centres its content vertically (a block with a height gives it room), and takes an optional `children` snippet drawn between the description and the action (Svelte use only: it is not a prop of `<scribe-empty-content>`, and the empty video lists its providers with it). It takes an optional `action` ({ label, onclick }), drawn as a button below the message. The default blocks use `valueDialogStore.getAction(...)` to offer to set or change their value in edit mode.
- `components/bindings/BindingsFloatingPanel.svelte` (`<scribe-bindings-panel>`) lists the document variables grouped by data type (`groupByType` in `utils/dataTypes.ts`), each group foldable with `aria-expanded`. A search opens every group, so no result is hidden. The type icon is `utilComponents/TypeIcon.svelte` and the type name `getTypeLabel` (same file as `groupByType`): use them instead of copying icon markup or label maps.
- `TextInput` and `Select` take a `label` (drawn above the field). `Dialog` is `Dialog` > header, scrolling body and footer; the body already scrolls, so do not nest another scroll area in a dialog unless a list needs its own (the variable list of `ComponentValueDialog` does, for its sticky search).
- `components/toolbar/TopToolbar.svelte` is the ribbon. `components/sections/ParagraphSection.svelte` renders the content of a section with `components/content/ComponentFlow.svelte`, which builds the ghost texts. `components/defaultComponents/*` are the built-in components.
- i18n lives in `i18n/locales/en.ts`, `es.ts` and `types.ts`. Every new key goes in all three. Use `getI18n()` and `i18n.t('a.b')`. `i18n` is a module-level singleton, so stores and utils can import it (`import { i18n } from '$lib/i18n/i18n.svelte.js'`) without receiving it as a parameter.
  - **Every text the user can see goes through i18n**: labels, tooltips (`title`), `aria-label`, `alt`, placeholders, the names of the registry options (`defaultRegistry.ts`, group `options.*`), the detail line of the error box (`errors.*`) and the data the document shows as text (a boolean is `common.true`/`common.false`, a new text is `common.newText`). Texts in a prop default cannot call `i18n`: read them inside the component (`label ?? i18n.t(...)`).
  - **These stay in English on purpose:** `console.warn`/`console.error` and the errors thrown by stores and utils (diagnostics for developers, never drawn in the UI), the sample content in `src/lib/examples` and in the default chart data, and the four default options in `ComponentEditOptions.ts` (a fallback: `ComponentEditor` shows `toolbar.*` for them).
  - `i18n/locales.test.ts` fails when `en` and `es` differ in keys, have an empty text, or use different `{placeholders}`. The vitest config does not compile runes, so no test can import the `i18n` singleton itself.
- Styling uses the `--scribe-*` CSS variables in `styles/scribe.css` (light and `.dark`). See "Styling rules" below.

## Behaviour that is easy to break

- **Text formatting:** the editable is the working copy of a text until it loses the focus (when `parseDOM` saves it), for typing and for formatting. Every text runs `syncFormatState` on the document's `selectionchange` and tells `text-format-store` where the caret or marked fragment is, with its formats. With a marked fragment, `toggle` calls back `formatSelection` in the text, which rewrites the editable from the string with `toggleTextFormat` (`utils/textFormat.ts`) and marks the fragment again, so the focus never moves and a ghost needs no special treatment. With only a caret it sets a pending format, which the text applies on `beforeinput` by inserting a formatted span. The pending format is dropped when the caret moves. Paste and drop are also handled on `beforeinput` and insert only the plain text (`text/plain`) of what comes, so images, files and HTML never reach the editable. The special characters of a stored text are ` * _ ~ -`: `tokenizeFormattedText` (`utils/textFormat.ts`) is the only reader of the stored format: the rendering of a text and `getFormatsInRange` are built on its tokens, so a new format character is added in the constants and `FORMAT_CHARS` only. `utils/textFormatEscape.ts` escapes them (derived from the constants, so the list cannot drift) and removes empty toggles without touching escaped ones. Spans created by hand have no Svelte scope class, so the `is-*` styles are `:global` inside `.edit-text`. **Colour:** a text can colour a fragment, stored with its own markers because it needs a value: `{#rrggbb}` sets the colour from there on and `{#}` goes back to the theme colour (`COLOR_CHAR`, independent of the toggles, so they interleave freely). A `{` is only a marker when exactly `#rrggbb}` or `#}` follows (checked with `isHexColor`), so any other brace in an old text stays literal, and `escapeSpecialChars` escapes every `{` in a new one. A colour ends at the end of its line, as the template tokenizes line by line, so `tokenizeFormattedText` resets it at each newline and `setTextColor` (the writer, in `utils/textFormat.ts`) sets it again at the start of each line of a fragment; `normalizeColorMarkers` drops markers that change nothing and `readEditableContent` runs it on every save. Spans carry `data-color` (what `parseDOM` reads back) and an inline `color` (what draws it, in edit and view mode). `TextFormats.color` is null for the theme colour and for a fragment of mixed colours. The store's `setSelection` takes a `TextFormatTarget` (`toggle`, `setColor`), and `setColor` sets the pending colour at a caret like `toggle` does for a format. Hosts that read the text of a document see these markers, as they already see `*` and `_`.
- **Unknown component types:** a component whose type is not in the registry (for example a custom type saved in a document and opened on a page that does not register it) renders the error box, with Set value disabled, instead of throwing, so the rest of the document still renders. `ComponentRenderer` and `TopToolbar` read `globalRegistry.components[type]` for this. The `globalRegistry.get*` getters throw for an unknown type, so do not call them on a render path without checking it first.
- **Slots:** a slot is an editable area inside a component that works like a section (the cells of the table are slots). `components/content/ComponentSlot.svelte` (public only as the custom element `<scribe-component-slot>`, never as an exported Svelte component: see "Two runtimes" below) draws one with a `ComponentFlow`, the same flow a section uses. The holder keeps its slots in its record value: the entry `slotKey` is a record of components keyed by their **ids**, in order, and a missing entry is an empty slot. `utils/componentSlots.ts` (tested) reads and writes that shape, finds the slot of a component (`findSlotOf`) and re-keys the slots of a clone, as the ids change when duplicating. A ghost text in a slot carries its `SlotRef` in `GhostComponentMeta.slot`, and `ToolbarInsertion.slot` makes the toolbars insert there. `ComponentFlow` binds every DOM lookup to its own flow (`.component-flow`, `closestOwned`/`queryOwned`), as a slot is a flow inside the component of another one. `ComponentRenderer.handleSelect` ignores events from inside a slot of its component, or a ghost text of a cell would select the whole table. `navigateToAdjacentComponent` skips the lines of another column when the caret is inside a slot (`.scribe-component-slot`), so ArrowUp/Down stay in the column. The table is the one holder with a grid: its cells are keyed `row:col`, so deleting a row or column renumbers the later keys with `utils/tableCells.ts` (tested), and the round delete handles on its border live in `TableComponentScribe.svelte` (outside the table, which clips). The README documents the public side.
- **Rows of a custom binding:** `CustomBinding.renderItem` (public, optional) lets the host draw the inside of each row of that binding in the value selector (`ComponentEditorBindingSelector.svelte`, the only place those rows are drawn). It is framework-agnostic on purpose, so Scribe stays headless: `(node, props) => { update?, destroy? } | void`, with `BindingItemProps` as plain data (`$state.snapshot` of the value, never a proxy or a store) and no HTML-string contract (an injection hole). Scribe owns the `<button class="binding-row">` (selection, `aria-pressed`, disabled, focus, keyboard, search by title, id, preview and type, tooltip, focus ring), so the content must not hold buttons or links. **Who draws what:** by default Scribe also draws the frame of the row (border, background, padding, the primary border, outline and wash when chosen, the dashed dimmed state when disabled), the `.scribe-check` and the Incompatible pill. With `CustomBinding.bareItems` (public, optional, only with `renderItem`; the store reads it with `hasBareItems`) the button gets `is-bare` and Scribe draws none of that: `display: block`, no padding, border or background, a `--scribe-radius-xl` radius so the focus ring follows the card of the host, `cursor: not-allowed` when disabled, and `.items-list.is-bare` has more padding so the ring is not cut by the scroll area. The host draws the frame, the check and the dimmed state from `isSelected` and `isDisabled`. A row whose renderer threw (`failedIds`) goes back to the framed default row, bare or not. `createItemHost` (`utils/bindingItemRenderer.ts`, tested) keeps the errors of the host code out: a throw while mounting makes that row show the default content (`failedIds`), and one in `update` or `destroy` is only logged. The rows of the default bindings, the binding-type cards of the dialog and the floating panel are not customisable. The selector reads each value once, so a subscribable binding does not tick in the open list. The examples show both ways to write a row on `full-edit-custom-binding`: the live clock is a Svelte component with `bareItems` that draws its own card and check (`src/lib/examples/LiveClockRow.svelte`, mounted with `createSvelteItemRenderer` of `src/lib/svelte/mount.svelte.js`, the public `@antonii22/scribe2/svelte`; the page also passes its context, which the row reads with `getContext`) and `custom-binding` is plain DOM, to show that the contract needs no framework. **The host's content gets none of the tag resets of Scribe:** the `<span class="row-custom" data-scribe-host>` that holds it is excluded from every rule that targets an element by its tag inside `.scribe-document` (`span`, `p`, `h1`-`h6`, `a`, `button`, `input`..., and the `border-color` of `*`), with `:not(:where([data-scribe-host], [data-scribe-host] *))` appended to each selector (it adds no specificity). Without it, a host that uses Tailwind v4 lost `text-xs`, `font-semibold` or `border-red-500` inside its rows. The content inherits the font and colour of the row, and the browser's default margins are the host's to reset. A new tag-only rule in `scribe.css` or `Scribe.svelte` must carry that suffix. Not excluded on purpose: `:focus-visible`, scrollbars, reduced motion and the rules by Scribe class. The attribute is a public opt-out, documented in the README ("Content drawn by the host"): a registry component of the host can put `data-scribe-host` on its root. Scribe does not set it on `.component-mount` itself, as the built-in components rely on the resets, so renaming the attribute changes a published API.
- **Checkbox:** the inline `checkbox` is the bits-ui `Checkbox.Root`, a square of `1lh` so it is as tall as a line of text. Like `text-input` its value is always a binding (`initialValue` makes `generateDefaultDataValue` create a boolean variable), and a click saves with `updateComponentValue(..., 'onblur')` in edit and view mode. A button has no caret, so `handleArrowNavigation` does not apply: the component calls `navigateToAdjacentComponent` for the plain arrows itself. Its class is `:global(.scribe-checkbox.scribe-checkbox)` because the child element is not scoped and has to beat the button reset.
- **Video:** the iframe `src` is built by `parseVideoUrl` (`utils/videoEmbed.ts`, tested) from the id it parses, on a fixed host of YouTube (nocookie) or Vimeo, and the typed link is never copied into it, so keep any new provider in that function. An iframe swallows the pointer events, so in edit mode a layer covers it until the component is selected, or a click on the video would never select it.
- **QR:** `qr-code-styling` is a dev dependency like the rest of the libraries, as `vite.wc.config.ts` bundles them all into `dist/scribe.js` (only `svelte` is a peer). Only the action of `QrComponentScribe.svelte` touches it, and it loads it with `import()` when the first code is drawn, as the library needs the DOM. The package is a CommonJS file that exports the class itself while its types describe an ES module, so the component reads the default export in both shapes and types the part it uses by hand. The code is a fixed 300px SVG scaled with CSS and black on white unless the user picks other colours (the theme never changes them). `config.dotsType` (`square` by default, `rounded`, `dots` for circles, `classy`) is the `dotsOptions.type` of the library, set from the ribbon group of the QR, and the code is always built and updated with the whole `dotsOptions` object, so a partial update never depends on how the library merges options. The library draws every dot as a shape inside one clip path, which leaves thin light seams where dots touch (each shape is anti-aliased on its own, and a stroke on a clip child is ignored), so `closeSeams` (in the library's `applyExtension` hook) moves the shapes into a `.qr-dots` group with a non-scaling stroke of the same colour. `config.dotsColor`, `cornersColor` (both black) and `backgroundColor` (white) are `#rrggbb` and fall back to their default when missing or invalid; they are set from the Color group of the ribbon (three `createColorOption`). `config.cornersType` (`square` by default, `rounded`, `dots` for circular) sets the shape of the three corners from the Corners group, and the component maps it to the two library types (`CORNER_SHAPES`): the library types say the corners take the dot types, but it only draws a frame of `square`, `extra-rounded` or `dot` and a centre of `square` or `dot`, so there is **no classy corner**. Corner shortcuts are `Alt+Shift+5-7`, as `Alt+Shift+1-4` are the dots and a shortcut cannot repeat in one component. Everything goes to the library as whole option objects, on creation and on every update. The library throws on a text that does not fit, and the component shows an error card then.
- **Colour picker option:** `createColorOption` (`registry/colorOption.ts`, public) returns a `ComponentEditOptions` whose `render` mounts `components/componentOptions/ColorPickerOption.svelte`: a `ComponentEditorButton` as the bits-ui `Popover.Trigger` (ghost, with a wide swatch of the colour as its icon) and a palette (`utils/colorPalette.ts`, tested: 11 columns, main row and 5 rows of shades). The choice is saved in `config[configKey]` as `#rrggbb`, and every reader must check it with `isHexColor` before it reaches markup or a library. `render` receives getters that follow the component, so the factory keeps them with `Object.getOwnPropertyDescriptors` instead of spreading. The popover portals into the `.scribe-portal-target` found from the button (`closest('.scribe-document')`), as an option that mounts itself has no Svelte context: it keeps the theme tokens, and `KEEP_SELECTION_SELECTOR` keeps the selection when clicking in it. The hidden `<input type="color">` for "More colours" is next to the button, not inside the popover, so it survives the popover closing before the native picker reports. It reports on `change`, when the picker closes, and the click that closes it (in the text) has already moved the caret and dropped the marked fragment, so `openNativePicker` keeps the target first with the optional `ColorAccessors.holdTarget` (the text uses `textFormatStore.holdColorTarget()`, which keeps the fragment and its range; a colour in a component config needs none). `ColorPickerOption` reads and writes the colour through accessors (`getColor(target)`, `setColor(color, target)`), so `createColorPickerOption` (`registry/colorOption.ts`, internal) serves two cases: the public `createColorOption` (the colour is `config[configKey]`, `resettable` adds an Automático row that deletes the key (with an info icon next to it that explains it in a tooltip, `colorPicker.automaticInfo`; the tooltip is a sibling of the row button, as a button cannot hold a button), `isDisabled` is passed on) and the colour of a text (the `format-color` option in the Format group, which reads `textFormatStore.activeFormats.color` and calls `textFormatStore.setColor`). Without a `label` the button is the option's icon with a bar of the colour under it. With `keepTextFocus` (the text) the panel opened with the mouse takes no focus and cancels `mousedown` inside it, or the text would blur, save and lose its marked fragment; opened from the keyboard it takes the focus (the store still holds the fragment) and the focus returns to the button on close.
- **Ghost texts:** empty places to write are synthetic texts (ids `__ghost_*`) that are not in the document. A text component is created on blur or when a component is inserted, and its `<span>` is recreated whenever the stored value changes (`{#key rawValue}`). The ghost alone in its flow (an empty section, or an empty slot with the id `__ghost_slot_<parentId>_<slotKey>`) is a full width line as tall as a line of text, so typing in it does not move the text when it is saved. Only the one of a section shows `editor.emptySectionPlaceholder`. The ghosts between two blocks keep a taller box with margins. `editStore.sectionToFocus` makes `ParagraphSection` put the caret in a section that has just been added.
- **Two runtimes: never export a Svelte component from `index.ts`.** `dist/scribe.js` carries its own copy of the Svelte runtime, and the reactive state (active effect, context) lives in the runtime that compiled the component. Tested in an external Vite app (Svelte 5.57.0, the bundle's version, installed from `npm pack`), in dev and in a production build: a bundle component rendered inside a host component renders, takes typing and `Ctrl+Space`, and is destroyed cleanly (listeners come back to the baseline), **but it does not follow props that depend on a host signal**. The host `$state` is read by host-compiled code with the host's `active_reaction`, which is null inside the bundle's effects, so no dependency is registered. A `mode` driven by a host `$state` and a component inserted into the slot (`componentData` updated by Scribe, stored but not drawn) were stale, while a host-compiled element reading the same override updated at once. Scribe's own mode change only worked because it remounted the registry component. So the Svelte components of the bundle (`ComponentSlot`, `TextComponentScribe`, `TextInputComponentScribe`, `ImageComponentScribe`, `LatexComponentScribe`, `TableComponentScribe`) are no longer exported. A host draws a slot with the custom element `<scribe-component-slot>`, which keeps the runtimes apart through the DOM: Svelte sets its properties and the same test followed host signals, a mode change on the same node, and the inserted component was drawn. Only code that has no state of its own may be shared as source, as `@antonii22/scribe2/svelte` does. A test of this kind needs a throwaway app outside the repo (the playground compiles everything with one Svelte, so it cannot show it).
- **`documentchange` detail:** it is a `DocumentChangeDetail` (`{ document, customBindingUsages }`, public, exported from `index.ts`), built once in the effect of `Scribe.svelte` and used for both the `ondocumentchange` callback and the DOM event. `customBindingUsages` comes from `calculateDocumentBindingUsages(docSnapshot)` and not from `editStore.customBindingUsages`: the store keeps them in place (live `Set`s that would change under the host), exists only in edit mode, and the usages must belong to the document of the same event. `getCustomBindingUsages()` still reads the store, for the starting state or an answer between events. The initial document fires no event. The README documents it ("Events").
- **Dark mode (`isDarkMode`):** `Scribe.svelte` follows the rule of the CSS (a `.dark` sets the `--scribe-*` tokens, which the descendants inherit): dark when the root element or **any ancestor** has the class `dark`. `utils/darkTheme.ts` (tested, on a minimal node shape as there is no DOM in the tests) builds the chain with `getAncestorChain`, which also crosses shadow roots through their host, as `closest` would stop there while the CSS variables do not, and `hasDarkClass` decides. `classList` is not reactive, so a `MutationObserver` watches the `class` attribute of **each node of the chain**, and the effect disconnects it when it is cleaned up (unmount). Do not observe `<html>` with `subtree`: Scribe toggles classes all the time (hover, selected), so it would fire constantly. The `class` prop of the Svelte case is on the root element, so it is in the chain. The chain is taken at mount, so an element moved to another parent later keeps watching the old ancestors. `isDarkMode` reaches the components through `Section`, `ComponentRenderer` and its `update`, so a change reaches the mounted ones without remounting them.
- **Insertion at the caret:** Ctrl+Space and the ribbon's Add share `captureInsertionAtCaret` in `TextComponentScribe.svelte`, which returns a `ToolbarInsertion`. A ghost with typed content is first created as a real text and then split.
- **Finding a text in the DOM:** `data-component-id` is on the `ComponentRenderer` wrapper and also on the editable of a text, and the wrapper comes first. Use `findEditableText(scope, id)` (`utils/focusNavigation.ts`) to get the editable. A bare `[data-component-id=…]` query returns a wrapper that cannot hold the focus, so the caret disappeared after inserting a component.
- **Selection:** a non-empty component is selected through its wrapper (`pointerdown` and `focusin`). A ghost or empty text is an insertion point. `Scribe.svelte` clears the selection on a document-level `pointerdown` (capture phase) unless the target matches `KEEP_SELECTION_SELECTOR`. The ribbon (`.scribe-top-toolbar`) cancels `mousedown` so the text keeps its focus and caret.
- **z-index:** top toolbar 3, section handles 10, add-component dropdown 30, bindings panel 40, dialogs 50, tooltips 60.
- **Buttons:** `Button.svelte` variants are `default` (the primary, a solid blue), `secondary`, `soft` (a chosen toggle: accent wash, accent text, accent hairline), `outline`, `ghost`, `destructive` and `ghost-destructive`; sizes are `default`, `sm`, `lg`, `icon` and `icon-sm`. They are the global classes `scribe-btn-{variant}` and `scribe-btn-size-{size}`, with no inline styles, so a one-off size goes in its `style` prop.
- **Specificity:** the scoped reset in `scribe.css` sets `padding`, `font-*` and `color` on `.scribe-document button` and `input`, and the size and colour of headings, at specificity (0,1,1). A plain global class loses to it, so any rule for those properties needs two classes (see `Button.svelte`) or a Svelte-scoped selector (`.x.svelte-hash`, which is (0,2,0)). `:where()` is not enough against a host that uses Tailwind v4: its utilities live in `@layer utilities`, and an unlayered rule beats a layered one whatever its specificity, so the tag resets (such as the `.scribe-document span` rule of `Scribe.svelte`) would win over `text-xs` even with specificity 0. That is why the content a host draws is excluded with `data-scribe-host` (see "Rows of a custom binding"). Never move the resets into an `@layer`: they would lose to the global CSS of the host, which is what they protect against.
- **Whitespace:** working-tree files use CRLF and the `.svelte` files mix tabs and 4 spaces. Match the surrounding code. If a multi-line edit does not apply, suspect whitespace.

## Styling rules

- The package must not depend on Tailwind. All styles under `src/lib` are plain CSS: `<style>` blocks in the components (with `:global(...)` where needed, as the custom element uses `shadow: 'none'`) and the `--scribe-*` variables in `styles/scribe.css`.
- `styles/scribe.css` is the only global stylesheet: it holds the variables and the scoped reset that protects Scribe from host styles. `build:wc` copies it as is into `dist/` (Vite's own CSS output is overwritten), so global CSS must live there and never be imported from a component.
- Tailwind classes are allowed only in the SvelteKit example pages under `src/routes`, which exist just to show the library. Never use them in `src/lib`, and never add a dependency from the library on `tailwindcss`.
- **Design:** Scribe is meant to sit inside a modern SaaS app. Grey `--scribe-doc-background` desk, white cards (`--scribe-section-background`, `--scribe-popover`) with 1px `--scribe-border-color` hairlines, a blue primary (solid buttons, check marks), a soft blue wash for chosen toggles (the `soft` button variant), and the accent for selection, focus and bound values (it starts as the same blue; they are separate tokens). Data types are marked by one system, `.scribe-tile[data-type]` and `.scribe-pill[data-type]`, coloured by the `--scribe-type-*` tokens. Shadows are only for layers that float (`--scribe-shadow-float`). Chosen cards and rows get the primary border, an accent wash and a `.scribe-check`, never a coloured side bar.
- **Tokens are public API.** Hosts set the base tokens: `--scribe-doc-background/-foreground`, `-primary(-foreground)`, `-secondary(-foreground)`, `-section-background/-foreground`, `-popover(-foreground)`, `-border-color`, `-muted(-foreground)`, `-accent(-foreground)`, `-selection-color`, `-error`, `-error-foreground`, `-on-error`, `-type-*`, `-overlay`, `-shadow-*`, fonts, sizes and `--scribe-radius`. The derived ones (`-border-strong`, `-accent-wash`, `-accent-soft`, `-accent-text`, `-error-wash`, `-error-soft`) are `color-mix` of base tokens, declared in `scribe.css` on `:root`, `.dark` and the Scribe elements, dialog and dropdown content, so they follow a host or `.dark` override. A new element that is portalled out of those needs adding to that selector list. The dark theme is `.dark` or `:root.dark`, on `<html>`, a wrapper or the Scribe element.
- **Shared primitives** live in `scribe.css`: `.scribe-caps-label` (a small uppercase label of a field or group, never a kicker above a heading), `.scribe-count`, `.scribe-kbd`, `.scribe-tile`, `.scribe-pill`, `.scribe-check`. Use them instead of per-component copies.
- **No hard-coded colours** (hex, `rgb()`, `oklch()`, `white`) in components: use a token, or `color-mix` of tokens. The brand colours of the video providers (the badges of the empty video in `VideoComponentScribe.svelte`, set as `--tile` of a `.scribe-pill`), the QR code (black on white by default in both themes so scanners read it, in `QrComponentScribe.svelte`), colours of user data (chart series, and the swatches of the colour picker palette and its check mark) and monospace for code-like content (the LaTeX source in the error box) are the exceptions. Icons use `currentColor`.
- Every control needs a visible focus state (the global `:focus-visible` accent ring covers the default; the text being typed shows its caret instead) and an accessible name. The target is WCAG 2.x AA in both themes.
- New colours, radii, fonts and sizes should use the existing `--scribe-*` variables. Add a new base token (with its `.dark` value, and documented in the README) only when none fits.

## Working agreements

- Ask before adding dependencies, changing the data model or public API, or choosing between several reasonable architectures (give the options, a recommendation, and wait).
- Do not keep backwards-compatibility shims. Change signatures in place and update every caller, example and test page (`test/*.html`). This is a published package, so ask first when a change touches the exports of `src/lib/index.ts`.
- `PRODUCT.md` records product truth (users, positioning, constraints) for design work. Keep it current when those change.
- Plan non-trivial work before coding. Keep summaries for the maintainer short.
- **Keep this file up to date.** After a major or noteworthy change, update `AGENTS.md` in the same change. That includes new or removed commands, props, stores or registry contracts, moved or renamed files, new conventions, and new gotchas discovered the hard way. Remove statements that are no longer true instead of leaving them stale.
- **Never commit, push or publish.** Do not run `git commit` (including `--amend`) or `git push`, and do not publish the package (`npm publish` or any release step), even if a tool or a default instruction suggests it. Leave the changes in the working tree for the maintainer to review and commit.
- **The maintainer runs the dev server.** Do not start `npm run dev` (or any other server) yourself. Assume the playground is already running and ask for its URL or port if you need it (it may not be 5173). To test in the browser, use the Claude in Chrome tools against that server. If it is not reachable, ask the maintainer to start it. `npm run build:wc` stays your job when `/examples/full-webcomponent-edit` needs a fresh `dist/`.
- Finish each change with `npm run check`, eslint, `npm test` and `npm run build:wc`, and report failures instead of working around them.
